# F001 Research: 本地资料存储与边界

**Date**: 2026-09-03
**Scope**: F001 本地资料库的存储、隐私、接口边界和测试策略。

## Decision 1: 使用加密 JSON 文件作为首版资料存储

**Decision**: 定义后端无关的 ProfileStore 接口，首个实现为 EncryptedJsonProfileStore。资料序列化为一个版本化 JSON 文档，使用 AES-GCM 加密后保存到用户应用数据目录。随机的数据加密密钥由操作系统凭据存储托管；密钥和 API Key 均不写入资料文档。

**Rationale**:

- F001 是单用户、本地部署，规模目标只有约 500 个字段值和 100 条重复记录，整文档读写足够；
- 整体加密可减少字段名、表结构和其他元数据泄露；
- AES-GCM 同时提供机密性和完整性校验，便于检测篡改或损坏；
- 操作系统凭据存储避免把口令或密钥放进仓库、日志或普通配置；
- 依赖少、跨平台接口清楚，使用临时目录、伪造 keyring 和篡改文件即可覆盖主要测试。

**Alternatives considered**:

| 方案 | 静态安全 | 原子/事务 | 依赖与发布 | 测试复杂度 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 加密 JSON + OS keyring + AES-GCM | 整体加密，字段元数据暴露少 | 通过 temp + fsync + replace + 单写锁实现 | cryptography、keyring、platformdirs；较低 | 易覆盖篡改、密钥丢失和中断 | F001 首选 |
| sqlite3 + 应用层加密 | 可加密值或整块，但可能泄露表和大小元数据 | SQLite ACID 较强 | sqlite3 自带，仍需加密库 | 需要更多迁移和事务测试 | 未来查询/历史需求出现时评估 |
| SQLCipher | 页级透明加密 | SQLite ACID 较强 | 原生二进制、供应链审计、Windows/CI/版本迁移矩阵更复杂 | 原生矩阵复杂 | 首版不选，需求触发再评估 |

**Security boundary**: 该方案主要防止磁盘、备份文件和普通日志泄露；不承诺防护同一登录用户下已经取得本机权限的恶意进程或内存窃取。

## Decision 2: 密钥和文件失败时拒绝降级

**Decision**:

- 首次打开时生成随机 DEK，并写入 OS keyring；
- 文件已存在但 keyring 找不到对应密钥时，绝不生成新密钥覆盖原文件，报告不可恢复/需要恢复操作；
- 只允许经过产品验证的 OS keyring 后端；后端不可用、权限不足、返回空值或切换到不受信任的文件/内存后端时，拒绝写入明文；
- 解密失败、认证标签无效或文件被篡改时，只报告可识别错误并保留原文件；
- 完整删除时先删除或隔离加密快照并验证其不可再读取，再删除对应 keyring 引用；任一步失败都返回结构化 partial-failure，不静默声称已删；文件系统或 SSD 的物理擦除不作保证；
- 首次初始化若 keyring 写入成功但快照写入失败，不先删除该密钥导致残留文件失去恢复机会；保留可复用密钥或记录待清理的孤儿密钥；
- 导出是用户主动选择范围、路径并确认后的明文副本，导出后不自动上传。

**Rationale**: 静默生成新密钥或回退明文会造成不可逆的数据丢失或隐私泄露，违反 Constitution 的本地优先和可恢复原则。

## Decision 3: 原子写入和单写者边界

**Decision**: 每次保存在同一目录创建临时加密文件，完成 flush 和 fsync 后使用原子替换；通过单写锁/事务抽象拒绝并发 lost update。临时文件、备份文件和错误信息都不能包含明文资料。

**Rationale**: F001 不需要多进程并发，但必须能在进程中断、磁盘错误或重复提交时保留最近一次完整有效资料。

## Decision 4: 规则优先、F001 不调用 Agent

**Decision**: 字段类型、长度、日期、数字、枚举、多值、范围和敏感标记均由确定性验证器处理。F001 不解析 PDF/Word/OCR，不调用远程模型，也不保存对话上下文。后续 F002/F003 产生的候选必须经同一资料服务和用户确认后才能写入。

**Rationale**: 资料库是可信数据底座，不应把简单校验交给模型，也不应在基础 Feature 引入不必要的网络和长期记忆。

## Decision 5: 共享契约优先，补齐资料生命周期操作

**Decision**: 扩展和本地服务继续以 `packages/contracts/v0.1` 为唯一消息来源。PR #1 已将 `profile.read`、`profile.export`、`profile.delete` 的请求/响应、版本、确认、选择和错误语义合并到 `main`（merge commit `23b9d2b`）。F001 不复制主 Schema，也不私下定义另一套字段含义。

**Rationale**: Options Page 需要读取和管理资料；把生命周期消息集中在共享 Schema 中，可以让扩展和本地服务对版本、确认、选择和错误保持一致，并在运行时代码开始前完成可验证的边界冻结。

## Decision 6: 以本地 API 和页面做最小可用闭环

**Decision**: 领域服务通过窄接口提供读取、写入、删除和导出；本地 API 只监听 loopback，页面只负责展示和收集用户决定。具体端口认证和最终扩展通信方式由 F004 决定，不能改变领域层的安全不变量。

**Rationale**: 用户需要可操作的资料库，而不是只存在测试里的存储模块；同时把传输层隔离，避免 F001 提前锁死浏览器通信方案。

## Validation Plan

- 使用假的 keyring 和临时应用目录测试首次初始化、正常读写、篡改、InvalidTag、密钥丢失、磁盘写入中断和原子替换；
- 使用契约样例测试字段类型、范围、敏感确认、自定义字段冲突和删除语义；
- 用 API 客户端测试确认/取消、幂等请求、结构化错误和空状态；
- 用页面测试验证编辑取消、无效值保留、敏感字段确认、导出范围和删除二次确认；
- 用网络拦截测试证明 F001 的资料流程不产生个人资料出站请求；
- 所有公开 fixture 使用合成或脱敏值，不使用真实简历或 API Key。
