# 智能简历填写助手：阶段性产品与架构讨论记录

- 日期：2026-09-01
- 状态：讨论草案，尚未进入实现阶段
- 目标：记录目前已经讨论过的方向，作为后续产品设计和开发讨论的基础

> 说明：本文不是最终技术规格，也不是实现计划。后续如果目标、范围或安全边界发生变化，应在继续讨论后更新，或另行形成正式设计文档。

## 1. 产品愿景

构建一个面向招聘、校招及其他在线报名场景的智能填写助手：用户准备好自己的基本信息、教育经历、实习经历、项目经历、获奖情况和常用问答后，助手能够理解当前网页表单的语义，将合适的信息填入对应字段，并在不确定或有风险的地方请求用户确认。

产品希望满足以下长期目标：

1. 能处理大部分常见网页表单，而不是只适配单一网站。
2. 能处理多页流程、动态表单、重复的教育/实习/项目经历模块。
3. 能够以 Agent 形式观察页面、规划步骤、执行操作并验证结果。
4. 主要供个人使用，同时具备开源、可自部署、可替换模型提供商的能力。
5. 默认保护个人隐私，不把敏感资料无条件上传到第三方服务。

## 2. 初步形态判断：浏览器插件是主要入口

浏览器插件适合作为产品的主要用户入口和网页执行端，因为它可以在用户当前打开的页面中：

- 读取表单标签、占位文字、控件类型和页面上下文；
- 执行输入、选择、勾选、点击和翻页等操作；
- 监听页面动态变化并检查填写结果；
- 在侧边栏中显示匹配建议、置信度和待确认项。

普通网页应用通常不能直接操作另一个网站中的表单；桌面自动化则更容易受窗口、分辨率和页面改版影响。因此，插件更适合作为“手脚”，但不必承载全部智能逻辑。

## 3. Agent、模型、后端和插件的关系

这些词描述的是不同概念：

- **模型**：负责理解文本、推断字段含义和生成结果。
- **Agent**：把模型、任务状态、规则、工具调用和循环流程组合起来，负责“观察—规划—执行—验证”。
- **后端**：承载这些逻辑的运行位置，可以是云服务器，也可以是用户电脑上的本地服务。
- **浏览器插件**：负责连接网页、展示界面并执行真实的页面操作。

如果 Agent 独立运行在用户电脑上，那么它可以看作一个“本地后端服务”；插件就是它的客户端和网页执行器。Agent 不会直接拥有用户浏览器页面的全部控制权，而是返回结构化的动作计划，由插件在页面上执行。

一个典型动作计划可能表达为：

```text
字段“毕业院校” ← education.school
字段“最高学历” ← education.highest_degree
字段“是否接受异地工作” ← 需要用户确认
下一步 ← 点击“下一页”
```

## 4. 推荐的总体方向：本地优先的混合架构

当前最适合“个人好用 + 开源 + 可扩展”的方向是：

```text
网页
  ⇅
浏览器插件（TypeScript）
  ⇅ 本机通信 / 结构化消息
本地 Agent 服务（Python）
  ├─ Agent 核心逻辑和任务状态机
  ├─ 资料检索与字段匹配
  ├─ 模型适配层
  ├─ 本地加密资料库
  └─ 网站规则和用户纠正记忆
```

云端模型或云端运行环境可以作为可选能力接入，但不应成为本地个人使用的唯一依赖。以后如果需要在线同步、多人服务或集中运维，可以在不改变插件协议的情况下增加云端运行层。

## 5. Python 与 Java 的初步取舍

### 当前推荐：Python Agent + TypeScript 插件

选择 Python 的主要理由：

- 大模型调用、文本处理、结构化抽取、文档解析和本地模型接入的现成工具多；
- 适合快速验证字段识别、资料匹配和 Agent 流程；
- 该产品大部分时间在等待模型、网页、文件或用户确认，属于外部等待较多的任务，Java 的运行速度优势在早期通常不明显；
- 更容易让开源贡献者快速加入和修改。

这并不是说 Python 总是比 Java 快。对于大量本地计算、超高并发或企业级服务治理，Java 仍然可能更合适。未来也可以把云端控制层改为 Java，而不必改变 Agent 核心的接口。

### 什么时候考虑 Java

- 已有成熟的 Java/Spring 团队或基础设施；
- 产品演变为大型企业服务，需要大量并发和长期运行；
- 需要深度接入企业内部 Java 系统；
- 团队维护 Java 的效率明显高于 Python。

## 6. Python 轮子复用原则

可以复用 Python 的成熟包，但应“按边界选择”，不要一开始堆叠大型框架。

适合优先复用的能力包括：

- 本地 API 服务；
- 数据结构校验和协议定义；
- 模型提供商 SDK；
- SQLite 和本地数据访问；
- 加密、系统密钥保存；
- PDF、Word 和其他简历附件解析；
- 后续按需要增加 OCR、嵌入和检索能力。

初期不必把重型 Agent 框架、向量数据库、分布式任务队列和完整浏览器自动化全部引入。网页的实时操作主要由插件负责，Python 侧重点应是推理、状态、资料和策略。所有第三方包都应通过清晰的接口隔离、锁定版本，并尽量提供可选依赖。

## 7. Agent 的工作循环

建议把 Agent 设计成可观察、可暂停、可恢复的流程：

```text
观察页面
  → 建立表单结构
  → 匹配个人资料
  → 生成填写计划
  → 执行低风险操作
  → 验证页面结果
  → 继续、询问或交给用户接管
```

“Agent”不等于完全放任模型自由点击。应使用结构化动作、权限控制、置信度和验证步骤，避免模型直接输出不可审计的任意脚本。

## 8. 自动化等级和安全边界

目前讨论出的三种自动化等级：

1. **辅助模式**：识别字段并给出建议，用户确认后填写。
2. **监督式 Agent**：自动翻页、填写和校验；遇到不确定或敏感内容暂停询问。建议作为默认模式。
3. **全自动模式**：仅在用户明确授权的站点和任务中启用，最终提交仍建议保留确认点。

应明确保留人工接管的场景：

- CAPTCHA、人机验证、短信验证码和 OTP；
- 手写签名或复杂身份核验；
- 无法可靠判断含义的开放题；
- 身份证号、银行卡、薪资等敏感字段；
- 最终提交动作。

产品目标不是承诺“任何网页 100% 自动完成”，而是让常见表单覆盖率高、异常情况可解释、失败时能安全地交还给用户。

## 9. 隐私和安全原则

- 个人资料默认本地保存并加密；
- 发送到云端模型的内容尽量只包含必要的字段描述和脱敏上下文；
- 敏感值可以由插件在本地填入，不必发送原文；
- 本地 Agent 只接受本机插件的请求，不对公网开放；
- 对站点权限、模型调用和提交动作提供明确授权和记录；
- 保存填写前后的状态或操作日志，便于排查和恢复；
- 不以绕过验证码、反爬或网站安全措施为产品目标。

## 10. 当前考虑过的方案

### 方案 A：纯插件

安装简单，适合轻量规则和基础自动填充；但复杂 Agent、长流程状态、本地模型和资料管理会受到限制。

### 方案 B：插件 + 云端 Agent

模型能力和更新速度较好，跨设备方便；但需要处理隐私、成本、账号和服务器运维问题。

### 方案 C：插件 + 本地 Agent（当前推荐）

个人资料和任务状态可以留在本地，Agent 能力完整，也方便开源用户自行部署；代价是需要额外安装和打包本地服务。

## 11. 已形成的阶段性共识

1. 浏览器插件作为主要入口和网页操作端。
2. 产品应具备 Agent，而不只是固定字段替换脚本。
3. Agent 可以作为本地后端服务运行，插件作为客户端。
4. 当前倾向本地优先的混合架构。
5. 当前倾向 Python Agent + TypeScript 插件。
6. 模型提供商应可替换，支持本地模型和云端模型的不同组合。
7. 默认采用监督式自动化，敏感和最终提交动作保留人工确认。
8. 先做个人可用和安全，再考虑云端同步、多人服务和大规模部署。

## 12. 尚未决定、后续需要继续讨论的问题

- 第一批要重点支持哪些网站和表单类型；
- 浏览器范围（Chrome、Edge、Firefox 等）；
- 是否要求用户额外安装本地助手，以及如何做到一键安装；
- 默认使用本地模型、用户自己的 API，还是提供可选云端服务；
- 个人资料的标准数据结构和多份简历版本管理；
- 插件与 Agent 之间的动作协议；
- 网站适配器、用户纠正记忆和版本管理方式；
- 附件上传、文件选择和多页流程的处理策略；
- 测试、日志、错误恢复和安全威胁模型；
- 开源许可证、贡献方式和发布渠道。
